# 영수증 OCR API 설계 및 구현 결정사항

[OpenAPI 명세](openapi.json)의 `POST /api/v1/proxy/ocr` 계약과 처리 방식을 설명합니다. 내용이 충돌하면 OpenAPI를 따릅니다. 외부 OCR 연동은 구현했고 가상 데이터로 실제 Azure 호출을 확인했습니다. 실제 영수증과 개발 VM 검증은 아직 완료되지 않았습니다.

## 확정된 계약

- Bearer 인증과 multipart `files` 배열을 사용하며 파일은 1~10개입니다.
- JPEG·PNG·HEIC·PDF를 허용하고 파일당 크기는 최대 10,000,000바이트입니다.
- 파일별 OCR 호출 제한은 60초이며 자동 재시도하지 않습니다.
- 일부 파일이 실패해도 입력 순서대로 파일별 성공·실패 결과를 반환합니다.
- OCR 결과는 거래 필드와 같은 store_name/date/time/amount를 사용하고 거래를 자동 저장하지 않습니다.
- 파일별 `azure_raw_result`에는 Azure 최종 분석 또는 HTTP 오류 본문을 담습니다. JSON 본문은 JSON 값, 그 외 본문은 문자열입니다. Azure가 분석에 성공했어도 서버에서 영수증 필드 변환에 실패하면 원본 본문을 돌려줍니다. 설정 누락이나 시간 초과로 최종 본문을 받지 못하면 `null`입니다.
- 선택적 `Idempotency-Key`를 지원합니다. 파일별 실패가 포함된 경우에도 HTTP 200 응답 전체와 Azure 원본 본문을 함께 저장해 24시간 동안 재사용합니다. 기존 저장 응답에 원본 본문이 없으면 `null`을 반환합니다.

## 측정 결과와 남은 결정

현재 구현은 프로세스당 OCR 외부 호출을 최대 두 개 동시에 처리하고, 검증된 파일은 임시 파일에 보관한 뒤 개별 호출에서 읽습니다. 2026-11-17 S0 개발 리소스와 가상 영수증으로 로컬에서 측정한 결과, 4,517,695바이트 PNG 1개는 약 5.7초, 작은 PNG 10개는 약 21.9초가 걸렸습니다. 10개 시험의 Python 추적 메모리 피크는 약 3.2MiB였으며 프로세스 전체 메모리가 아닙니다. 2026-11-18에는 외부 호출을 모의한 로컬 TestClient로 9,990,990바이트 PNG 10개가 HTTP 200으로 처리되는 것을 확인했으며 클라이언트와 서버를 합친 프로세스의 최대 작업 집합은 320.5MiB였습니다.

2026-11-19 개발 VM의 별도 컨테이너에서 실제 Azure에 연결해 893,277바이트 한국 영수증 이미지 1개는 5.3초, 동일 이미지 10개는 24.7초에 모두 성공했습니다. 소비 분석도 HTTP 200으로 2.4초에 완료했습니다. 시험 컨테이너는 CPU 0.5개·메모리 700MiB로 제한했고 독립 DB를 사용했습니다. Python 최대 RSS는 208,404KiB, cgroup 메모리 피크는 192,876,544바이트였습니다. 이는 서버와 시험 클라이언트를 포함하는 단일 컨테이너의 측정이며 실제 Caddy·네트워크 경로나 장시간 운영에 대한 결과는 아닙니다.

같은 격리 환경에서 외부 OCR을 모의한 부하 시험은 9,950,372바이트 PNG 10개 요청을 4.3초에 처리했고, 동일 크기 파일 2개씩을 담은 두 요청의 동시 처리도 1.3초에 성공했습니다. Python 최대 RSS는 217,780KiB, cgroup 메모리 피크는 350,359,552바이트였습니다. 이 측정은 동일 프로세스의 ASGI 시험 클라이언트와 서버를 포함하고, 외부 OCR 지연과 실제 프록시 경로는 포함하지 않습니다.

2026-11-19 VM에서 Caddy 2.11.4를 별도 포트로 실행하고 독립 컨테이너에 TCP로 연결해 실제 Azure 호출을 시험했습니다. 893,277바이트 영수증 1개는 4.7초, 10개는 27.7초에 모두 성공했고, 1개씩 동시 요청 2건은 각각 4.7초·3.9초에 성공했습니다. 소비 분석도 3.3초에 성공했습니다. 이 경로는 VM 내부의 HTTP이며 기존 공개 HTTPS 서버와 프로세스가 분리되어 있습니다. 기존 공개 HTTPS 버전 API의 HTTP 200과 HTTP→HTTPS 리디렉션도 별도로 확인했습니다. 기존 공개 서버에는 이 기능이 배포되지 않아 공개 HTTPS에서 새 기능까지의 전체 경로는 미검증입니다.

같은 별도 Caddy 경로에서 외부 OCR을 모의했을 때 9,940,898바이트 PNG 10개 요청은 4.8초, 동일 크기 파일 2개씩을 포함한 두 동시 요청은 각각 0.6초·0.8초에 성공했습니다. 모의 시험의 시간에는 실제 Azure OCR 처리 시간이 포함되지 않습니다.

여러 페이지 PDF를 Azure는 페이지별 문서로 반환할 수 있어 필드를 합칩니다. 서로 다른 핵심 값이 인식되거나, 두 페이지 이상에서 각각 상호와 총액이 함께 인식되어 별도 영수증일 가능성을 배제할 수 없으면 파일별 실패로 반환합니다. 이 기준에서는 실제로 한 영수증이라도 상호와 총액이 여러 페이지에 반복되면 실패할 수 있습니다. 필드가 누락된 여러 영수증은 구분하지 못할 수도 있어 실제 영수증으로 추가 검증이 필요합니다.

2026-11-19 [KORIE 공개 한국 영수증 샘플](https://github.com/MahmoudSalah/KORIE/tree/main/Samples) 두 장을 로컬 API와 실제 Azure로 시험했습니다. 두 장 모두 상호·날짜·품목을 반환했고, 한 장의 결제금액은 Azure가 총액 필드를 반환하지 않아 `null`이었습니다. 두 영수증을 합친 PDF는 실패 처리됐습니다. 한 영수증을 상·하 두 페이지로 분할한 PDF도 양쪽에서 상호와 총액이 인식돼 구분이 불확실하므로 실패했습니다. 두 장만으로 실제 서비스의 전반적인 인식률을 추정할 수 없고, 필드 누락이나 페이지별 반복 인식은 사용자 확인이 필요합니다.

측정 결과 동기 요청으로 안정적으로 완료할 수 있으면 전체 제한 시간과 최대 병렬 처리 수를 정해 이 문서와 OpenAPI에 반영합니다. 최악 처리 시간이 앱이나 프록시의 요청 제한을 넘으면 `202 Accepted` 기반 비동기 작업 생성·상태 조회 API로 전환합니다. 이 결정을 내리기 전까지 OpenAPI는 파일별 60초 제한만 보장하며 전체 요청 제한 시간이나 순차·병렬 처리를 보장하지 않습니다.
